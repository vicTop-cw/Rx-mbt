## 2. 逐项修法

### 2.1 C3-Q4（P2）给「篡改信封」负向用例加门禁

**改的文件**：`scripts/verify_interop.py`（唯一改动文件）

**问题回顾**：fixture 的 `envelope` 有 3 例（含 `tampered_checksum`），生产者只产出 2 例；
`--strict` 只要求"已产出的分节齐全"，不会因缺负向用例报错 ⇒ 「MoonBit 能否拒绝被篡改信封」跨实现零证据。

**修法**：`check_envelope()` 增加负向覆盖检查（枚举 fixture 中 `expect_error: true` 的用例，
比对产物条目名）：

```python
produced_names = {i.get("name") for i in items}
missing_negative = sorted(n for n in tamper if n not in produced_names)
if missing_negative and (expected or items):
    detail = "产物未包含负向（篡改）用例 %s ⇒ 「拒绝被篡改信封」无跨实现证据" % ",".join(missing_negative)
    report.add("envelope", "negative-coverage", "FAIL" if require_negative else "WARN", detail)
```

配套：
- `Report.render_console()` 排序表加入 `WARN`（`FAIL > WARN > SKIP > PASS`）；
- 汇总行改为 `PASS=x FAIL=x WARN=x SKIP=x`；
- `RESULT: PASS` 文案在存在 WARN 时追加「⚠ N 项 WARN（互操作盲区请加 --require-negative 门禁）」；
- `--out` 机器可读报告的 `counts` 增加 `warn`；
- 新增 CLI 开关 `--require-negative`（默认关闭 ⇒ 不改变既有用法与退出码）。

**自测矩阵**

| 场景 | 命令 | 期望 | 实测 |
|---|---|---|---|
| 默认 `--strict` | `verify_interop.py moonbit_vectors_full.json --strict` | `WARN=1`，**rc=0**（不破坏 C1/C2 语义） | ✅ `PASS=46 FAIL=0 WARN=1 SKIP=0`，rc=0 |
| 门禁模式 | 追加 `--require-negative` | `FAIL=1`，rc=1 | ✅ rc=1，首项 `envelope/negative-coverage` |
| 普通模式（无 `--strict`） | 不带开关 | rc=0，仍提示 WARN | ✅ |
| 校验器自检 | `--self-test` | 5 个场景全 OK | ✅ 5/5 OK（正向/对抗/部分/扁平非strict/扁平strict/分节strict） |
| 回归不破 | `--out` 报告 | `counts.warn` 存在 | ✅ 见 `interop-verify` 类报告 |

> 说明：WARN **不影响退出码**是刻意的 —— 它表达的是"证据缺口"而不是"不一致"；
> 等生产者补上 tampered 用例后，把 `--require-negative` 打开即可变成硬门禁（移交项见 §5）。

## 4. 为什么**没有**改 fixture（刻意决策）

C3-Q4 的另一半（schema 与产物字段漂移：生产者多 `checksum_match`、schema 列的 `bytes_utf8_hex` 未产出）
理论上可以靠重新生成 fixture（扩 `moonbit_objects_schema` 说明）修掉，但：

1. `vools_vectors.json` sha256 `f22dda48…` 已写进 C1/C2 多份报告与 verify 结论，**改 sha 会打断证据链**；
2. 该漂移**不造成误判**（`verify_interop` 对 `bytes_utf8_hex`/`to_rhop_bytes_utf8` 都接受，`checksum_match` 是冗余字段）；
3. 真正的缺口（缺 tampered 产物）属生产者，不是 fixture 的问题。

⇒ 本轮只加**工具侧门禁**，fixture 保持 `f22dda48…` 不变。
